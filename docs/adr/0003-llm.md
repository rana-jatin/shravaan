# ADR 0003 — Sarvam-105B as the reasoning model

**Status:** Accepted · **Date:** 2026-08-29

## Context

The LLM sits between ASR and TTS on every turn. It drives the 250 ms first-token allocation
in [03](../03-latency-budget.md), the data-residency story, and — as it turns out — the
system's concurrency ceiling.

## Decision

**Sarvam-105B** (`sarvam-105b`, with `sarvam-105b-conversations` as a variant to evaluate).

> **Amended 2026-08-30.** The variant was evaluated and is now the default. We run
> **`sarvam-105b-conversations`**; `sarvam-105b` is unusable for speech. See the addendum at the
> foot of this ADR for the measurements.

## Options considered

### Sarvam-105B — chosen

- **In-India inference.** Sarvam self-hosts all models and states "Data residency in India"
  ([overview](https://docs.sarvam.ai/conversations/overview.md)). With Sarvam already
  carrying ASR and TTS, keeping the reasoning hop in-country means no part of an Indic
  session leaves India.
- **Indic-native.** Documented for 11 languages (10 Indian + English) and listed for
  "complex reasoning, real-time dialogue, voice agents"
  ([models](https://docs.sarvam.ai/api/getting-started/models)).
- **Cheap.** ₹29.28 per 1M input tokens, ₹10.98 cached input, ₹73.2 output
  ([pricing](https://docs.sarvam.ai/api/getting-started/pricing)). The cached-input tier is
  roughly a third of fresh input, which implies prompt caching exists and is worth
  structuring the prompt around.
- **One vendor, one contract, one support relationship** across all three stages.

### Claude / other external LLM — rejected

Stronger tool-calling and instruction-following, and no comparable rate ceiling. Rejected on
residency: the reasoning hop would leave India while ASR and TTS stayed, which is a worse
compliance story than either "all in" or "all out". If tool-calling quality proves
insufficient during [slice 6](../04-milestones.md#slice-6--tools-and-fillers), this is the
first thing to revisit.

### Deepgram-managed LLM — rejected

Deepgram's Voice Agent API supports OpenAI, Anthropic, Google, Groq and Bedrock, plus BYO
via `agent.think.endpoint` ([configure](https://developers.deepgram.com/docs/configure-voice-agent.md)).
Irrelevant here — we rejected that orchestrator ([ADR 0001](0001-orchestrator.md)), and its
LLM options are only reachable from inside it.

### Defer behind an abstraction — rejected

Leaves the latency budget and the residency claim unresolved, and adds a layer before we
know what varies. The cascaded design ([ADR 0002](0002-cascaded-vs-speech-to-speech.md))
already makes the LLM swappable at the stage boundary; a further abstraction buys nothing
today.

### Deprecated, for the record

`sarvam-m` and `sarvam-30b` are **deprecated and no longer available through the API**
([models](https://docs.sarvam.ai/api/getting-started/models)). Noted because they appear in
older material and would be a natural wrong turn.

## Consequences

### The rate limit is the system's concurrency ceiling

| Plan | Sarvam-105B | STT WebSocket concurrent | Bulbul v3 TTS concurrent |
|---|---|---|---|
| Starter | **40 req/min** | 20 | 30 |
| Pro | **60 req/min** | 100 | 200 |
| Business | **120 req/min** | 100 | 1000 |

Source: [rate limits](https://docs.sarvam.ai/api/getting-started/ratelimits).

At a plausible 3–5 LLM calls per active conversation-minute, **Starter supports roughly 8–13
concurrent conversations and Pro roughly 12–20** — below the STT socket limit in both cases.
Capacity plans against the LLM, and the plan tier is a scaling decision, not a billing one.

This also constrains a latency optimisation: speculative LLM starts
([03 §6](../03-latency-budget.md#6-policies-that-buy-latency-back)) spend requests to buy
milliseconds, and requests are the scarce resource. It cannot be enabled blindly.

### First-token latency is unmeasured

Sarvam publishes **no latency figure** for any model. The 250 ms allocation in
[03](../03-latency-budget.md) has no documented basis. If it lands beyond ~450 ms, the
filler policy has to expand from tool calls to ordinary turns — a change to the product's
personality, not its configuration.

### Prompt discipline is a latency and cost decision

The profile caps in [02](../02-data-contracts.md) — 30 facts, 10 episodes, 5 open threads —
exist partly for this. Prompt size drives first-token latency and is charged on every turn.
Keep the stable prefix genuinely byte-stable so the cached-input tier applies.

### Tool-calling quality — **ANSWERED**, 2026-08-29

Nothing in the documentation we read described Sarvam-105B's tool-calling reliability, and
the tool contract in [02 §5](../02-data-contracts.md#5-tool-call-contract) assumed structured
calls work well. That assumption has now been run against a live key —
`npm run verify:tools`, source in [`scripts/verify-tool-calling.ts`](../../scripts/verify-tool-calling.ts).

**It speaks OpenAI's dialect, and the fallback to an external LLM is not needed.**

| Probe | Result |
|---|---|
| `tools` accepted; a call is emitted | Yes |
| Delta shape | `{index, id, type, function:{name, arguments}}` — OpenAI-compatible |
| Long arguments | Fragment token by token, exactly as OpenAI streams them |
| `tool_choice` `auto` / `none` / `required` / named | All four honoured |
| Parallel calls in one round | Yes — two calls returned together |
| `strict: true` | Accepted (whether it is *enforced* is untested — we validate locally regardless) |
| `role:"tool"` result round-trip | Works; answers in prose |
| Full loop through our own client + registry + executor | Reaches a spoken answer |

**One divergence, and it fails silently.** For a short or empty argument object Sarvam sends
the finished value whole and then sends it *again*:

```
frame 55  {"arguments":"",   "name":"get_time"}
frame 56  {"arguments":"{}", "name":null}
frame 57  {"arguments":"{}", "name":null}      ← the same value, twice
```

OpenAI's contract is that fragments concatenate to exactly one JSON value, so the obvious
`args += fragment` produces `{}{}`, `JSON.parse` throws, and the original parser's catch
emitted **empty arguments**. For a no-argument tool that is accidentally correct; for any
other it is silent data loss, surfacing as a companion that ignores half of what it is told.
Handled in `accumulateArgs` in [`src/providers/sarvam-llm.ts`](../../src/providers/sarvam-llm.ts),
with the captured frames as a regression test.

The general lesson is the same one the ASR and TTS protocols taught: on this provider, assume
nothing is right merely because it does not throw.

### Making it narrate its own tool calls

A tool call that streams no text leaves the user in silence until the result lands. The model
saying what it is about to do is strictly better than our own filler copy: specific to the
question, and fluent in all eleven languages — including the nine where our progress lines are
still placeholder text awaiting a native speaker.

It does not do this by default, and asking politely does not help. Preamble rate, counted only
over runs that actually called a tool:

| System prompt | Preambled |
|---|---|
| No instruction | **0/9** |
| Polite instruction, mid-prompt | 0/3 |
| Forceful imperative alone | 1/3 |
| Few-shot priming messages alone | 0/3 |
| Few-shot priming + forceful imperative | 6/8 |
| **Forceful imperative + inline example** | **7/9** ← shipped |

Two findings worth carrying to any future prompt work on this model. **Describing a behaviour
achieves almost nothing; describing it forcefully and showing an example achieves it** — and
neither lever works alone. And the example does **not** need to be a real priming message: an
inline one performs the same and avoids inserting an invented exchange into the conversation
history, where the model can later refer back to a day that never happened.

At ~78% this is an improvement, not a guarantee. Roughly one tool turn in four still begins in
silence, so the per-tool `ProgressKey` copy remains the floor rather than a fallback, and each
new slow tool still costs eleven translations.

> **Superseded for the shipped model, 2026-08-30.** Every figure in the table above was measured
> against `sarvam-105b`. We now run `sarvam-105b-conversations` (see the addendum below), and the
> prompt does **not** transfer: re-measured twice on the same nine asks with the same shipped
> `SYSTEM_PROMPT`, the rate is **2/9 — 22%**, identical across both runs. Both preambles were the
> two Hindi asks; all five English asks called silently.
>
> The finding underneath still holds — describing a behaviour forcefully with an inline example is
> what moved it on the previous model — but the specific wording is tuned to a model we no longer
> use. Re-tuning it against this one is open work.
>
> The consequence is smaller than the inversion implies. Time-to-first-tool-call on this model is
> 0.64–1.73 s (median 1.05), and the built-in tools execute in single-digit milliseconds, so an
> un-preambled turn is silent for about a second. The same turn on `sarvam-105b` was silent for
> ~12.8 s. The preamble is now a nicety; it was previously load-bearing.

**Still unmeasured:** selection *quality* under a realistic tool count, and behaviour when the
conversation is in an Indic language while tool descriptions are in English. Both need a live
conversation, not a probe.

## Addendum, 2026-08-30 — the variant is the model

`sarvam-105b` is a **reasoning model**, and nothing on the endpoint announces it. Its deltas
carry a `reasoning_content` field alongside `content`; it fills the former with thousands of
characters before it emits a single token of the latter. Read only `content` — as any
OpenAI-shaped client does — and the stream simply appears to stall.

Both models are live on `/v1/models`. Measured over 12 identical calls each, same prompt:

| | `sarvam-105b` | `sarvam-105b-conversations` |
|---|---|---|
| First `content` token, median | **12,777 ms** | **313 ms** |
| Range | 11,273–15,052 ms | 225–562 ms |
| Completed with speech | 7/12 | **12/12** |
| Completed empty | 3/12 | **0/12** |
| Dropped connection | 2/12 | **0/12** |
| `reasoning_content` per turn | 4,876–7,754 chars | **0** |
| Tool-calling contract (`verify:tools`) | 7/7 | **7/7** |

Three things follow.

**The latency disqualifies it outright.** [03](../03-latency-budget.md) allocates 250 ms to the
first token. The clause chunker exists to begin synthesis at the first clause boundary, and it
cannot begin before a clause exists — so on the reasoning model the entire streaming design
buys nothing, and the user waits about thirteen seconds in silence. No amount of downstream
tuning recovers that.

**The empty completions were the same fault, not a second one.** Reasoning burn is what
exhausted capacity; the failures clustered after seven calls and cleared after a 75 s cooldown.
Sarvam sheds load as a well-formed 200 with zero content deltas, or as a dropped socket —
**never a 429**. Any retry policy keyed on 429 is guarding a door nobody uses.

**Reasoning cannot be switched off.** `reasoning_effort` is accepted and validated
(`low`/`medium`/`high`; anything else is a 400) but showed no measurable reduction.
`chat_template_kwargs.enable_thinking=false`, `thinking.type=disabled` and
`separate_reasoning=false` are all accepted and all ignored. The variant is the only way out.

### Carried over — do not delete on the strength of the swap

- **The `{}{}` argument retransmission still occurs** on the conversations model.
  `accumulateArgs` stays.
- **`max_tokens` counts reasoning tokens.** On `sarvam-105b`, `max_tokens: 700` returns
  `finish_reason: "length"` with 2,713 chars of reasoning and **zero content** — a silent mute
  switch. Harmless only while the reasoning model is unused; `StreamOptions.maxTokens` is still
  public API.
- **Reasoning can bleed into `content`.** `sarvam-105b` was observed emitting a literal
  `</think>` and several hundred words of internal monologue as spoken text. Nothing in
  `src/` strips it.

### Known and off the product path

`tool_choice: "required"` degenerates on the conversations model: it emits the call, then loops
whitespace to the token cap (87 s, `finish_reason: "length"`, 3,037 chars). Intermittent — a
later run of the same check was clean. The orchestrator only ever sends `"auto"` and `"none"`
(`src/orchestrator/session.ts`), so this is unreachable in production. Keep it that way, and
expect check 4 of `verify:tools` to be slow when it bites.
