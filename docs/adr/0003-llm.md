# ADR 0003 — Sarvam-105B as the reasoning model

**Status:** Accepted · **Date:** 2026-08-29

## Context

The LLM sits between ASR and TTS on every turn. It drives the 250 ms first-token allocation
in [03](../03-latency-budget.md), the data-residency story, and — as it turns out — the
system's concurrency ceiling.

## Decision

**Sarvam-105B** (`sarvam-105b`, with `sarvam-105b-conversations` as a variant to evaluate).

## Options considered

### Sarvam-105B — chosen

- **In-India inference.** Sarvam self-hosts all models and states "Data residency in India"
  ([overview](https://docs.sarvam.ai/conversations/overview.md)). With Sarvam already
  carrying ASR and TTS, keeping the reasoning hop in-country means no part of an Indic
  session leaves India.
- **Indic-native.** Documented for 11 languages (10 Indian + English) and listed for
  "complex reasoning, real-time dialogue, voice agents"
  ([models](https://docs.sarvam.ai/api/getting-started/models)).
- **Cheap.** ₹29.28 per 1M input tokens, ₹10.98 cached input, ₹73.2 output
  ([pricing](https://docs.sarvam.ai/api/getting-started/pricing)). The cached-input tier is
  roughly a third of fresh input, which implies prompt caching exists and is worth
  structuring the prompt around.
- **One vendor, one contract, one support relationship** across all three stages.

### Claude / other external LLM — rejected

Stronger tool-calling and instruction-following, and no comparable rate ceiling. Rejected on
residency: the reasoning hop would leave India while ASR and TTS stayed, which is a worse
compliance story than either "all in" or "all out". If tool-calling quality proves
insufficient during [slice 6](../04-milestones.md#slice-6--tools-and-fillers), this is the
first thing to revisit.

### Deepgram-managed LLM — rejected

Deepgram's Voice Agent API supports OpenAI, Anthropic, Google, Groq and Bedrock, plus BYO
via `agent.think.endpoint` ([configure](https://developers.deepgram.com/docs/configure-voice-agent.md)).
Irrelevant here — we rejected that orchestrator ([ADR 0001](0001-orchestrator.md)), and its
LLM options are only reachable from inside it.

### Defer behind an abstraction — rejected

Leaves the latency budget and the residency claim unresolved, and adds a layer before we
know what varies. The cascaded design ([ADR 0002](0002-cascaded-vs-speech-to-speech.md))
already makes the LLM swappable at the stage boundary; a further abstraction buys nothing
today.

### Deprecated, for the record

`sarvam-m` and `sarvam-30b` are **deprecated and no longer available through the API**
([models](https://docs.sarvam.ai/api/getting-started/models)). Noted because they appear in
older material and would be a natural wrong turn.

## Consequences

### The rate limit is the system's concurrency ceiling

| Plan | Sarvam-105B | STT WebSocket concurrent | Bulbul v3 TTS concurrent |
|---|---|---|---|
| Starter | **40 req/min** | 20 | 30 |
| Pro | **60 req/min** | 100 | 200 |
| Business | **120 req/min** | 100 | 1000 |

Source: [rate limits](https://docs.sarvam.ai/api/getting-started/ratelimits).

At a plausible 3–5 LLM calls per active conversation-minute, **Starter supports roughly 8–13
concurrent conversations and Pro roughly 12–20** — below the STT socket limit in both cases.
Capacity plans against the LLM, and the plan tier is a scaling decision, not a billing one.

This also constrains a latency optimisation: speculative LLM starts
([03 §6](../03-latency-budget.md#6-policies-that-buy-latency-back)) spend requests to buy
milliseconds, and requests are the scarce resource. It cannot be enabled blindly.

### First-token latency is unmeasured

Sarvam publishes **no latency figure** for any model. The 250 ms allocation in
[03](../03-latency-budget.md) has no documented basis. If it lands beyond ~450 ms, the
filler policy has to expand from tool calls to ordinary turns — a change to the product's
personality, not its configuration.

### Prompt discipline is a latency and cost decision

The profile caps in [02](../02-data-contracts.md) — 30 facts, 10 episodes, 5 open threads —
exist partly for this. Prompt size drives first-token latency and is charged on every turn.
Keep the stable prefix genuinely byte-stable so the cached-input tier applies.

### Tool-calling quality is unverified

Nothing in the documentation we read describes Sarvam-105B's tool-calling reliability. The
tool contract in [02 §5](../02-data-contracts.md#5-tool-call-contract) assumes structured
calls work well. **[Slice 6](../04-milestones.md#slice-6--tools-and-fillers) is the real
test**, and the honest fallback if it disappoints is an external LLM with the residency cost
that implies.
